# תרגיל — בלק ג'ק (Backend + DB + Frontend)

## 0. מטרת התרגיל

בניית משחק בלק ג'ק מלא (Backend + DB + Frontend) מול "דילר" ממוחשב עם חוק פשוט וברור: הדילר שולף קלפים כל עוד סכום היד שלו קטן מ-17, ועוצר ברגע שהגיע ל-17 ומעלה. תרגיל מתוחם ליום עבודה אחד, עם דגש על ארכיטקטורה נקייה: זיהוי פשוט בלי אותנטיקציה מלאה, ולידציות מפורשות, ותכנון DB עצמאי.

---

## 1. הרעיון

שחקן משחק בלק ג'ק מול המחשב (הדילר). **חוק הדילר יחיד וברור:** הדילר שולף קלפים כל עוד סכום היד שלו קטן מ-17, ועוצר ברגע שהגיע ל-17 ומעלה (או פרץ מעל 21).

## 2. ישויות (ייצוג JSON — לבחירת הנבחן איזה DB לממש)

### 2.1 Player

```json
{
  "id": "string/number",
  "chips": "number, >= 0",
  "createdAt": "datetime"
}
```
- **אין username/password בכלל** — הזיהוי הוא מזהה אנונימי (`playerId`) שנוצר בעת `/start-game` ונשמר ב-localStorage.
- `chips` בעת יצירה: **תמיד 1000 בדיוק** (`STARTING_CHIPS = 1000`).

### 2.2 Round (סבב משחק)

```json
{
  "id": "string/number",
  "playerId": "מזהה של Player קיים",
  "bet": "number, > 0",
  "playerCards": [ { "rank": "2..10 | J | Q | K | A", "suit": "hearts|diamonds|clubs|spades" } ],
  "dealerCards": [ { "rank": "...", "suit": "..." } ],
  "status": "in_progress | player_bust | dealer_bust | player_win | dealer_win | push",
  "createdAt": "datetime"
}
```
- כלל מפורש: **לשחקן מותר סבב `in_progress` אחד בלבד בו-זמנית.** אי אפשר לפתוח סבב חדש כל עוד יש סבב פתוח — חייבים לסיים אותו קודם (הפסד/ניצחון/תיקו).
- חפיסת קלפים: **אין ניהול חפיסה עם הסרה** (כדי לא להצטרך state של חפיסה). כל שליפת קלף היא הגרלה אחידה בלתי-תלויה מתוך 13 דרגות × 4 סוגים (52 אפשרויות), כאילו יש חפיסה אינסופית. זה מפשט מאוד את השרת ומספיק לגמרי לרמת התרגיל.

---

## 3. חישוב ערך יד — כלל מפורש

- דרגות 2–10: ערך = הדרגה עצמה.
- J, Q, K: ערך = 10.
- A (אס): ערך = 11 **או** 1 — לוקחים את הערך הגבוה ביותר שלא עובר 21. כלומר: מחשבים תחילה עם כל האסים כ-11, ואם הסכום עולה על 21, מורידים אסים אחד-אחד מ-11 ל-1 (כל פעם מוריד 10 מהסכום) עד שהסכום ≤21 או שאין יותר אסים להוריד.
- **פיצוץ (bust):** אם גם עם כל האסים כ-1 הסכום עדיין >21 — היד פרצה.
- **אין התייחסות מיוחדת ל"בלק ג'ק טבעי"** (21 בשני הקלפים הראשונים) — הוא מנוצח כמו כל ניצחון רגיל, בלי תשלום מיוחד של 3:2. זו הפשטה מכוונת.

---

## 4. חוק תשלומים — כלל מפורש

- בפתיחת סבב: `chips -= bet` **מיד**.
- אם השחקן פרץ (`player_bust`): אין תשלום נוסף — ה-bet כבר ירד, `chips` לא משתנה יותר.
- אם השחקן ניצח (`player_win` / `dealer_bust`): `chips += bet * 2` (מחזיר את ההימור פי 2 — כלומר רווח נטו של `bet`).
- אם תיקו (`push`): `chips += bet` (מחזיר בדיוק את ההימור, בלי רווח והפסד).
- אם הדילר ניצח (`dealer_win`): אין תשלום נוסף.

## 5. אנדפוינטים

### מידלוור זיהוי (זהה בדיוק לדפוס של מבחן הצבאות)
- Header: `x-player-id`.
- שולף Player מה-DB לפי id, אם לא קיים → 401.
- מצרף `req.player`. **אין** אימות טוקן/חתימה — סימולציה בלבד, אותה החלטה פדגוגית כמו במבחן.

### מידלוור זיהוי
- Header: `x-player-id`.
- שולף Player מה-DB לפי id, אם לא קיים → 401. מצרף `req.player`.
- **אין שום אימות אמיתי** — `playerId` הוא מזהה אנונימי בלבד, בדיוק כמו `armyId` במבחן הצבאות.

### `POST /start-game`
- **Body:** ריק.
- **לוגיקה:** יצירת Player חדש עם `chips = 1000`.
- **תגובה 201:** `{ playerId, chips }` — הפרונט שומר `playerId` ב-localStorage ושולח אותו כ-`x-player-id` בכל בקשה מכאן והלאה.

### `POST /start-round`
- **Header:** `x-player-id`
- **Body:** `{ bet }`
- **ולידציה:**
  - `bet > 0` וגם `bet <= req.player.chips`.
  - **אין** לשחקן כבר סבב `in_progress` פתוח (אם יש → 409).
- **לוגיקה:**
  1. `chips -= bet`.
  2. שליפת 2 קלפים לשחקן, 2 קלפים לדילר.
  3. יצירת Round חדש עם `status: 'in_progress'`.
- **תגובה 201:** `{ roundId, playerCards, dealerUpCard, chips }` — **שימו לב:** מוחזר רק הקלף הראשון של הדילר (`dealerUpCard`), הקלף השני נשאר חבוי בשרת עד סוף הסבב. זה הרכיב ה"מגניב" של המשחק — המתח של הקלף הסמוי.
- **שגיאות:** 400 (bet לא תקין / אין מספיק chips), 409 (יש כבר סבב פתוח).

### `POST /hit`
- **Header:** `x-player-id` (פועל על הסבב הפתוח היחיד של השחקן — אין צורך ב-body)
- **ולידציה:** קיים סבב `in_progress` לשחקן (אחרת 404).
- **לוגיקה:**
  1. שליפת קלף נוסף לשחקן.
  2. חישוב ערך היד (סעיף 3).
  3. אם >21 → `status = 'player_bust'`, הסבב מסתיים (אין תשלום נוסף, הכל כבר ירד).
- **תגובה 200:** `{ playerCards, playerTotal, status, chips }`
- **שגיאות:** 404 (אין סבב פתוח).

### `POST /stand`
- **Header:** `x-player-id`
- **ולידציה:** קיים סבב `in_progress` לשחקן.
- **לוגיקה (תור הדילר — פונקציה טהורה מומלצת `playDealerTurn`):**
  1. כל עוד ערך יד הדילר (סעיף 3) < 17 → שולפים לו קלף נוסף וחוזרים על הבדיקה.
  2. ברגע שערך יד הדילר ≥17 (או שפרץ מעל 21) — הדילר עוצר.
  3. **קביעת תוצאה:**
     - דילר פרץ (>21) → `dealer_win = false`, `status = 'dealer_bust'`, השחקן מנצח.
     - שני הצדדים לא פרצו → משווים ערכים: שחקן>דילר → `player_win`; שחקן<דילר → `dealer_win`; שווה → `push`.
  4. עדכון `chips` לפי חוק התשלומים (סעיף 4).
- **תגובה 200:** `{ playerCards, dealerCards, playerTotal, dealerTotal, status, chips }` — כאן **כל** קלפי הדילר נחשפים, כולל הקלף שהיה חבוי.
- **שגיאות:** 404 (אין סבב פתוח).

### `GET /my-round`
- **Header:** `x-player-id`
- **לוגיקה:** מחזיר את הסבב הפעיל (`in_progress`) של השחקן, אם קיים — נחוץ כדי שהפרונט ידע לשחזר מצב אחרי רענון דף (המצב חי ב-DB, לא רק בזיכרון הדפדפן).
- **תגובה 200:** `{ roundId, playerCards, dealerUpCard, bet, status }` אם יש סבב פתוח, אחרת `{ round: null }`.

## 6. Frontend — Vanilla JS (עמוד אחד בלבד — אין login)

### `game.html`
- בעליית הדף: בדיקת `playerId` ב-localStorage. אם אין → קריאה אוטומטית ל-`/start-game`, שמירת התוצאה, ואז המשך.
- קריאה ל-`/my-round` לבדוק אם יש סבב פתוח (שחזור מצב אחרי רענון).
- אם אין סבב פתוח: טופס הימור (`bet`) וכפתור "התחל סבב" → `/start-round`.
- אם יש סבב פתוח: הצגת קלפי השחקן + `dealerUpCard` (קלף אחד בלבד, השני מוצג כ"קלף הפוך" ויזואלית), כפתורי **Hit** ו-**Stand**.
- אחרי `/stand`: הצגת כל קלפי הדילר, התוצאה (ניצחון/הפסד/תיקו), ועדכון יתרת ה-chips.
- הצגת `chips` נוכחיים בכל עת בראש הדף.

## 7. Docker / Tests / GitHub

- **Docker:** `Dockerfile` + `docker-compose.yml` — מחייב **רק** להעלות את השרת עצמו. **אין חובה שה-DB ירוץ בתוך Docker** (אפשר DB מקומי, שירות חיצוני, או אפילו in-memory — זו בחירה של הנבחן, לא נבדקת).
- **טסטים — ברמת קונטרולר/יוז-קייס בלבד, אין טסטי אינטגרציה בכלל** (כלומר: קריאה ישירה לפונקציית הקונטרולר/יוז-קייס עם קלט מדומה, לא הרמת שרת אמיתי ובדיקה מול DB אמיתי):
  - קונטרולר `/hit` — טסט שקורא לו ישירות ובודק את ההתנהגות (כולל מקרה של פיצוץ, כולל חישוב יד עם כמה אסים).
  - קונטרולר `/stand` — טסט שקורא לו ישירות ובודק את התוצאה (ניצחון/הפסד/תיקו, פיצוץ דילר).
  - **טסט נוסף, נפרד, על לוגיקת הדילר בלבד** — `playDealerTurn(dealerCards)` כפונקציה טהורה (מתי עוצר בדיוק ב-17, מתי ממשיך, מתי פורץ) — בלי קשר לקונטרולר.
  - `/start-game`, `/start-round`, `/my-round` — לא דורשים טסטים.
- **GitHub:** README קצר, קומיטים הגיוניים.
- **כלל אפס:** אם השרת לא עולה מ-`docker-compose up` — 0 על חלק ה-Backend.
