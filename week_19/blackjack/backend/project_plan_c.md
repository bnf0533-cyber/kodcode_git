# תרגיל — בלק ג'ק (Backend + DB + Frontend)

## 0. מטרת התרגיל

בניית משחק בלק ג'ק מלא (שרת + מסד נתונים + ממשק משתמש) מול "דילר" ממוחשב.

**חוק הדילר:** שולף קלפים כל עוד סכום היד קטן מ-17. עוצר מיד כשהגיע ל-17 ומעלה (או שפרץ מעל 21).

---

## 1. הרעיון וההפשטות המכוונות

* משחק לשחקן יחיד מול הדילר.
* **חפיסת קלפים מפושטת:** אין ניהול מצב חפיסה (אין צורך לעקוב אחרי קלפים שיצאו או לערבב). כל שליפה היא הגרלה עצמאית מתוך 52 האפשרויות הקבועות (13 דרגות × 4 צורות).
* **סבב פעיל יחיד:** לשחקן מותר להחזיק סבב אחד בלבד בסטטוס `in_progress`. אי אפשר להתחיל סבב חדש עד שהנוכחי לא מסתיים.

---

## 2. מבנה הישויות (DB Entities)

### 2.1 Player (שחקן)
```json
{
  "id": "string / number",
  "chips": 1000,
  "createdAt": "datetime"
}
```
* **ללא מערכת משתמשים/סיסמאות:** אין רישום, אין התחברות ואין JWT. הזיהוי מתבצע דרך `playerId` בלבד שנוצר בשרת ונשמר בדפדפן.
* `chips` התחלתי: **1000 בדיוק**.

### 2.2 Round (סבב משחק)
```json
{
  "id": "string / number",
  "playerId": "מזהה השחקן",
  "bet": 100,
  "playerCards": [
    { "rank": "10", "suit": "hearts" }
  ],
  "dealerCards": [
    { "rank": "K", "suit": "diamonds" }
  ],
  "status": "in_progress | player_bust | dealer_bust | player_win | dealer_win | push",
  "createdAt": "datetime"
}
```

---

## 3. חוקי חישוב ערך יד

* **2–10:** ערך מספרי רגיל.
* **J, Q, K:** ערך קבוע של 10.
* **A (אס):** מחושב תחילה כ-11. אם סך היד עובר 21, מורידים אסים לערך 1 (הפחתה של 10 לסכום לכל אס) עד שהסכום <= 21 או שנגמרו האסים.
* **פריצה (Bust):** סכום מעל 21 גם אחרי חישוב כל האסים כ-1.
* **בלק ג'ק טבעי:** אין יחס תשלום מיוחד של 3:2. 21 על ההתחלה משלם רגיל (1:1).

---

## 4. חוקי תשלומים וצ'יפים

* **פתיחת סבב:** הצ'יפים יורדים מיד (`chips -= bet`).
* **ניצחון שחקן (`player_win` / `dealer_bust`):** השחקן מקבל `chips += bet * 2` (החזר הימור + רווח).
* **תיקו (`push`):** השחקן מקבל חזרה את ההימור `chips += bet`.
* **הפסד שחקן (`player_bust` / `dealer_win`):** אין שינוי נוסף (ההימור כבר ירד).

---

## 5. אנדפוינטים ו-API

### מידלוור זיהוי (בדומה לדפוס ממבחן הצבאות)
* קורא Header בשם `x-player-id`.
* שולף את ה-Player מה-DB. אם לא קיים -> שגיאה `401`.
* מצמיד את האובייקט ל-`req.player`. זוהי סימולציה מופשטת ללא אימות חתימה אמיתי.

---

### `POST /start-game`
* **Body:** ריק.
* **לוגיקה:** יצירת Player חדש עם 1000 צ'יפים.
* **תגובה (201):**
  ```json
  { "playerId": "...", "chips": 1000 }
  ```

---

### `POST /start-round`
* **Header:** `x-player-id`
* **Body:** `{ "bet": number }`
* **ולידציה:**
  * `bet > 0` וגם `bet <= req.player.chips`.
  * בדיקה שאין סבב `in_progress` פתוח (אם יש -> שגיאה `409`).
* **לוגיקה:**
  1. ניכוי ההימור: `chips -= bet`.
  2. שליפת 2 קלפים לשחקן ו-2 קלפים לדילר (נשמרים ב-DB).
  3. יצירת סבב חדש בסטטוס `in_progress`.
* **תגובה (201):**
  ```json
  { "roundId": "...", "playerCards": [...], "dealerUpCard": {...}, "chips": 900 }
  ```
  *הערת מימוש:* ה-API מחזיר רק את הקלף הראשון של הדילר (`dealerUpCard`). הקלף השני נשאר חבוי בצד השרת עד לסיום הסבב.

---

### `POST /hit`
* **Header:** `x-player-id`
* **ולידציה:** קיים סבב `in_progress` פתוח לשחקן (אחרת שגיאה `404`).
* **לוגיקה:**
  1. שליפת קלף נוסף לשחקן.
  2. חישוב ערך היד.
  3. אם הסכום > 21: עדכון הסטטוס ל-`player_bust`.
* **תגובה (200):**
  ```json
  { "playerCards": [...], "playerTotal": 22, "status": "player_bust", "chips": 900 }
  ```

---

### `POST /stand`
* **Header:** `x-player-id`
* **ולידציה:** קיים סבב `in_progress` פתוח לשחקן (אחרת שגיאה `404`).
* **לוגיקה (תור הדילר — `playDealerTurn`):**
  1. הדילר שולף קלפים כל עוד ערך ידו < 17.
  2. ברגע שהגיע ל- >= 17 (או פרץ מעל 21) — הדילר עוצר.
  3. קביעת תוצאה: השוואת סכומים (`player_win` / `dealer_win` / `push` / `dealer_bust`).
  4. עדכון צ'יפים במידת הצורך.
* **תגובה (200):**
  ```json
  { "playerCards": [...], "dealerCards": [...], "playerTotal": 19, "dealerTotal": 18, "status": "player_win", "chips": 1100 }
  ```
  *הערת מימוש:* כאן נחשפים כל קלפי הדילר, כולל הקלף שהיה מוסתר.

---

### `GET /my-round`
* **Header:** `x-player-id`
* **לוגיקה:** מאפשר לפרונט לשחזר את תמונת המשחק לאחר רענון הדף מתוך ה-DB.
* **תגובה (200):**
  * אם יש סבב פתוח: `{ "roundId": "...", "playerCards": [...], "dealerUpCard": {...}, "bet": 100, "status": "in_progress" }`
  * אם אין סבב פתוח: `{ "round": null }`

---

## 6. Frontend — Vanilla JS (`game.html`)

* עמוד יחיד, ללא מסך התחברות.
* **טעינת הדף:** בדיקת `playerId` ב-`localStorage`. אם חסר -> קריאה ל-`/start-game`. לאחר מכן קריאה ל-`/my-round` לבדיקת סבב פתוח.
* **מצב ללא סבב:** הצגת טופס הימור וכפתור "התחל סבב".
* **מצב סבב פתוח:** הצגת קלפי שחקן, הצגת קלף גלוי אחד של הדילר + קלף הפוך ויזואלית, וכפתורי **Hit** ו-**Stand**.
* **לאחר סיום סבב:** חשיפת כל קלפי הדילר, הצגת תוצאת המשחק ועדכון מאזן הצ'יפים בראש הדף.

---

## 7. בדיקות ו-Docker

### בדיקות יחידה (Unit Tests בלבד)
* **ללא טסטי אינטגרציה וללא שרת חי:** הבדיקות מתבצעות ישירות על הפונקציות עם קלט מדומה.
* **מה לבדוק:**
  1. `playDealerTurn(dealerCards)`: פונקציה טהורה שבודקת עצירה ב-17 ומעלה, משיכה מתחת ל-17, ופריצה מעל 21.
  2. לוגיקת `/hit`: חישוב אסים ומקרה של פריצת שחקן.
  3. לוגיקת `/stand`: קביעת ניצחון/הפסד/תיקו/פריצת דילר.
* נתיבי `/start-game`, `/start-round`, `/my-round` אינם דורשים טסטים.

### סביבת Docker
* `Dockerfile` + `docker-compose.yml` להרמת שרת ה-Backend.
* אין חובה להריץ את ה-DB בתוך Docker (אפשר זיכרון מקומי / קובץ / שירות נפרד).
* **דרישת סף:** השרת חייב לעלות בהצלחה דרך `docker-compose up`.
